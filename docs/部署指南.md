# 部署指南

生产部署形态:**一台服务器 + Docker Compose 三件套**(Caddy 自动 HTTPS + 应用 + PostgreSQL)。
控制台前端已编译进 Go 二进制,API/控制台/支付回调同域名同进程,插件也只需要这一个域的权限。

```
用户/插件 ──HTTPS──> Caddy ──> app(:8090) ──> PostgreSQL
易支付回调 ──────────┘            ├─ .env(密钥,不入库)
                                 └─ prompts/private/(公开提示词,随仓库提交,运行时挂载)
```

## 一、前置条件

- 服务器一台(2C2G 起步足够),已装 Docker 与 Compose 插件(`docker compose version` 能跑);
- 域名一枚,**A 记录指向服务器 IP**;国内服务器需已完成 ICP 备案;
- 服务器防火墙/安全组放行 **80 与 443**(80 是证书签发必需,不能只开 443);
- 易支付商户参数(EPAY_URL/PID/KEY)、SMTP 发信账号。

## 二、首次部署

```bash
# 1. 取代码
git clone https://github.com/HPZS/ai-form-backend.git && cd ai-form-backend

# 2. 提示词随仓库一起 clone 下来了(2026-08-18 起入库),确认齐全即可
ls prompts/private/*.yaml   # 当前应有 23 个 yaml；新增能力时随仓库数量同步更新

# 3. 配置
cp .env.example .env
chmod 600 .env
openssl rand -base64 32     # 跑两次,分别填 JWT_SECRET 和 HASH_PEPPER
vim .env
```

`.env` 生产必填项:

| 变量 | 值 |
| --- | --- |
| `DOMAIN` | 你的域名(不带协议),Caddy 据此签证书 |
| `POSTGRES_PASSWORD` | 随机强密码 |
| `CALLBACK_ADDRESS` / `CONSOLE_ADDRESS` | 都是 `https://你的域名` |
| `JWT_SECRET` / `HASH_PEPPER` | 各自独立的 32 字节随机串,**上线后不可再改**(改了全员登录态与验证码失效) |
| `ADMIN_EMAILS` | 管理员邮箱,逗号分隔 |
| `SMTP_*` | 发信账号(QQ 邮箱:SMTP_SERVER=smtp.qq.com,SMTP_TOKEN 是授权码不是密码) |
| `EPAY_*` | 易支付商户参数 |

`LISTEN_ADDR`/`DB_DSN`/`TRUSTED_PROXIES`/`PROMPTS_DIR` 不用管——compose 会为容器强制指定。

```bash
# 4. 起服务(镜像从 Docker Hub 拉取 hupeng666/form-backend,服务器无需构建)
docker compose up -d
docker compose logs -f app   # 看到 "ai-form-backend 启动于 :8090" 即成功
```

数据库建表、默认套餐/能力单价播种全部在启动时自动完成。

## 三、上线检查单(按顺序)

1. 浏览器打开 `https://域名`,证书有效、控制台登录页正常;
2. 用 `ADMIN_EMAILS` 里的邮箱走验证码登录(**顺带验证了 SMTP 收信**),确认左侧出现"系统管理"菜单;
3. 系统管理 → **能力配置**:设置默认模型;
4. 系统管理 → **AI 上游**:添加至少一个 OpenAI 兼容上游(建议两个以上,故障自动切换);
5. 系统管理 → **套餐管理**:确认价格(基础版 9.9/1000、进阶版 59.9/10000,可改);
6. 普通邮箱注册一个测试号 → 购买基础版走**真实易支付**支付 9.9 元 → 确认积分到账、流水正确(这笔钱是自己的,等于免费验证了回调链路);
7. 插件按生产域名构建后加载,登录、识别一张表单,确认扣分与徽章刷新。

## 四、日常运维

```bash
docker compose logs -f app          # 应用日志
docker compose ps                   # 状态
docker compose restart app          # 重启应用(改了 .env 后)
```

**发布新版本——铁律:镜像只在开发机构建,服务器只拉取,禁止在服务器上构建。**
Docker Hub(hupeng666/form-backend)是唯一镜像源:服务器构建会产生与 Hub 不一致的同名镜像,
版本无法追溯、回滚标签失去意义,还会在服务器上残留构建缓存与悬空镜像。

开发机执行(PowerShell 同理):

```bash
docker compose build app
docker tag hupeng666/form-backend:latest hupeng666/form-backend:$(git rev-parse --short HEAD)
docker push hupeng666/form-backend:latest
docker push hupeng666/form-backend:$(git rev-parse --short HEAD)
```

**服务器升级**(只拉镜像;数据库迁移在应用启动时自动执行):

```bash
cd /opt/ai-form-backend
docker compose pull app && docker compose up -d app
docker compose logs --tail 20 app   # 看到 "ai-form-backend 启动于 :8090" 即成功
```

注意:生产服务器的 `/opt/ai-form-backend` **不是 git 仓库**,只放 docker-compose.yml、.env 与
prompts/private;compose 或提示词有变化时从开发机手动同步(scp),不要在服务器上 clone 源码。

2026-09 任务 Agent 契约为 `APIRevision 16`，新增 `read_source_image.yaml`，更新 `match_columns.yaml` v7 和 `agent_task_step.yaml` v2。升级时同步整套提示词并保留原目录备份，再拉取镜像和重建 app；保持服务器现有代理、Compose 与 `.env` 配置。`GET /v1/about` 应返回 `apiRevision: 16`，日志中全部提示词加载成功。旧插件接口继续兼容，新插件遇到低于 16 的后端会明确停止并提示升级。

2026-09-08 发布记录：镜像 `hupeng666/form-backend:2ee7216`（同时更新 latest），digest 为 `sha256:1f3beaf6a80010a455c16d16b08b339dadc83ecfa0b604f9f971c3d95b270e43`。开发机完成构建推送，服务器仅拉取并重建 app；23 份 private 提示词同步，关键图像/任务提示词 SHA256 与开发机一致。公网 `/v1/about` 已核实为 16。旧镜像记录与提示词备份保存在 `/opt/ai-form-backend/releases/20260908-api16/`。后续 `ee93b76` 只修正测试中的提示词版本预期，生产代码和部署镜像一致。

**改了提示词就要 scp**:提示词不打进镜像(容器按 `./prompts/private:/app/prompts/private:ro` 挂载宿主机目录),
所以只 `docker compose pull` 是拉不到新提示词的。同步办法:

```bash
# 开发机(覆盖前先在服务器上留一份,提示词改坏了要能退回去)
ssh 服务器 'cd /opt/ai-form-backend/prompts/private && cp match_columns.yaml match_columns.yaml.bak-$(date +%F)'
scp prompts/private/match_columns.yaml 服务器:/opt/ai-form-backend/prompts/private/
```

改提示词时**必须同时把文件顶部的 `version:` 加一版**——AI 响应会把它回传给插件,
取证包里能一眼看出线上跑的是哪一版,忘了同步就查得出来。

出问题回滚:把 compose 里 app 的镜像改成上一个提交号标签再 `docker compose up -d app`
(每次发布都带提交号标签,Hub 上可查)。

**备份**(每日 3 点 pg_dump,保留 14 天)——`crontab -e` 加:

```cron
0 3 * * * cd /path/ai-form-backend && docker compose exec -T postgres pg_dump -U aiform aiform | gzip > /var/backups/aiform-$(date +\%F).sql.gz && find /var/backups -name 'aiform-*.sql.gz' -mtime +14 -delete
```

建议再把 `/var/backups` 同步到对象存储/异地一份。**恢复**:

```bash
gunzip -c aiform-日期.sql.gz | docker compose exec -T postgres psql -U aiform aiform
```

## 五、插件正式包(内测阶段)

API 地址是构建期烧进插件的,在插件仓库(ai-auto-form)执行:

```powershell
$env:AIFORM_API_BASE = 'https://你的域名'
npm run build        # 产物 .output/chrome-mv3,开发者模式加载即内测
npm run zip          # 提交商店用的 zip(内测通过后再提审)
```

注意:换过 `AIFORM_API_BASE` 后重新构建,**必须在 chrome://extensions 重载扩展并刷新业务页面**才生效。

## 六、安全边界(不可违反)

- `.env` 永不提交仓库、永不打进 Docker 镜像(.gitignore / .dockerignore 均已排除);
- `prompts/private/` **随仓库提交**(2026-08-18 起,本仓库是公开的 AGPL 项目,等于公开发布)——
  换来的是版本历史、备份与"换台开发机 clone 就能跑";但仍**不打进镜像**,
  容器按只读卷挂载宿主机目录,所以改了提示词要 scp(见上节);
- 数据库端口不对外暴露(compose 未映射 5432,仅容器网络内可达);
- 应用容器以非 root 运行,前端资源在二进制内,服务器上没有可被篡改的静态目录。



## 计费 v2 发布（APIRevision 17）

本次保持线上匹配 50、生成 1、其余 21 项 0 的单价，变更的是逐次收费与资金协议。`billingProtocolVersion: 2` 随 `/v1/about` 返回。新的积分调用必须携带 taskId、requestId 和已确认的 authorizationVersion；旧客户端新的积分调用返回 426，旧成功请求继续重放。发布完成后用户需要重新加载新版插件并刷新业务页面。

迁移增加计费分类/价格版本、请求摘要、请求预留、任务价快照、结果与缓存到期时间、关联返还和唯一索引；AI 请求状态列扩为 32 字符。历史流水不补扣、不重写；重复迁移已在 PostgreSQL 16 独立 schema 通过。部署前检查旧 `subscription_plans.trial` / `capability_prices.temperature` 不存在，防止触发早期开发阶段的破坏性旧迁移。

本机验收：`go test ./...`；实际并发验收通过 `AIFORM_BILLING_TEST_DSN` 指向本机 `aiform_billing_test` 执行 `go test ./internal/credits -run TestPostgresBillingConcurrency -count=1 -v`。制造 8 行真实模型浏览器与控制台返还结果保存在插件仓库的本机 `.artifacts`；后端 `cmd/billing-eval-server` 只能连接本机专用验收库，不连接生产业务库。

备份目录 `/opt/ai-form-backend/releases/20260908-billing-v2/` 已留数据库 dump、目录清单、Compose、环境文件、23 份提示词和旧镜像 ID。发布前原流水 152 条（最大 ID 152），原字段摘要 `b5318d996e83b8a5287fafd2d1cf5e3b`，没有有效在途请求。发布后按原 ID 范围再次核对摘要，避免正常新增记录干扰历史对账。

紧急止损使用 **当前兼容版本** 的 `BILLING_PAUSED=true` 并重建 app：只暂停新的积分调用，原 ID 重放、待结算恢复、订阅包含功能与账单继续可用。恢复时设为 false。**禁止直接回退到 APIRevision 16 或更早镜像继续接受 AI 计费请求**；旧二进制不理解请求预留和新预算，可能破坏账务。不要恢复旧数据库覆盖新流水。

本次未修改提示词；服务器保持原挂载目录、Compose、代理和密钥。本机构建并推 Docker Hub，服务器仅拉镜像并重建 app。本次部署镜像 `hupeng666/form-backend:663095f`（latest 同步），digest `sha256:0dc082aae434b9571b78b247b7ffdfd982ccda054247e74c228cb6975dae13bd`，运行镜像 ID `sha256:552afdb07e772f5016a30f01629859197bea5de8c9cb84b9b0e700f9713e630d`。公网 `/v1/about` 已验证 APIRevision 17 / billingProtocolVersion 2 / per-call-v2，BILLING_PAUSED=false；应用运行，数据库健康，控制台资源为本次构建。历史 ID ≤ 152 的流水条数和原字段摘要均与备份前一致；价格 50/1/其余 0、23 项均启用、价格版本 1。代码镜像与后续发布记录提交仅文档/验收脚本有区别。

## 动态能力计费发布（APIRevision 18）

任意能力可以切换 included / per_call。启动强制所有能力启用，但不覆盖原模式、积分单价或价格版本；不新增表结构，不重写历史请求和流水。新调用核对当前模式及单价，旧报价失效；已受理的请求与原请求重放继续使用自身快照。报价新增通用 calls 计数并兼容旧字段，计费协议仍为 2。

能力配置移除启停项；购买页增加实时能力价格表。服务和插件需配套更新，插件要求 APIRevision ≥ 18；旧插件调用新增收费能力会被明确拒绝，不能绕过收费。部署保留全部现有价格，不把“生成规则可配置”误当作立即修改生产价格。

本机构建镜像与 web/dist，服务器只 pull。发布前备份数据库、Compose、环境配置和镜像 ID，并保存历史流水摘要及价格目录；发布后核对历史 ID 范围摘要与目录。若需止损使用当前兼容版本 BILLING_PAUSED=true；旧 API17 不能解释任意收费目录，不直接退回旧镜像继续接收新 AI 请求。

本机验证：go test ./...；动态网关/目录/模式切换/日限流/种子保留回归；PostgreSQL 并发测试在独立 schema 通过。cmd/billing-config-eval 使用内存数据库、本机模拟上游和虚构管理员，只监听 127.0.0.1:18097，供购买页和管理页浏览器联动验收，不能代替真实供应商成本验证。
